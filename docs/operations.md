# Эксплуатация

## Сброс пароля

В облачном Supabase восстановление работает через ссылку «Забыли пароль?» на странице входа: Supabase отправляет письмо со ссылкой, ссылка ведёт на `/auth/callback`, затем на страницу нового пароля. В настройках проекта Supabase нужно указать адрес сайта и разрешённый redirect `https://<домен>/auth/callback`, а также подключить свой SMTP: встроенная почта Supabase подходит только для проверки.

Локально письма не уходят наружу, их принимает Mailpit: http://127.0.0.1:54324. Если удобнее без почты, пароль меняется командой

    npm run user:password -- foreman.petrov@demo.local новый-пароль

Скрипт использует service role ключ из `.env.local` и работает только там, где этот ключ есть.

## Очистка временных загрузок

Фото загружаются до отправки отчёта, поэтому после закрытой вкладки или ошибки сети остаются временные файлы. Команда

    npm run cleanup:uploads

удаляет из хранилища и базы временные загрузки старше 24 часов и файлы, на которые нет записи в базе. Фото опубликованных отчётов не удаляются. В пилоте команду стоит запускать по расписанию раз в сутки на сервере, где есть service role ключ.

## Резервная копия: база вместе с фотографиями

Копия состоит из двух частей, и одна без другой бесполезна: данные базы (схемы `public`, `app` и `auth`, то есть задания, история, отчёты, сотрудники и их пароли) и файлы бакета `task-photos`. Структуру базы, функции, политики доступа и сам бакет повторно создают миграции из репозитория, поэтому вместе с копией сохраняется список применённых миграций. Выгрузка таблиц в CSV копией не является: в ней нет пользователей и самих фотографий.

Порядок важен: сначала база, потом файлы. Опубликованные фото никогда не удаляются и не перезаписываются, поэтому все файлы, на которые ссылается дамп, гарантированно окажутся в копии хранилища, снятой позже. Лишние временные файлы в копии не мешают, их уберёт очистка.

Команды выполняются из корня проекта, для облачного проекта после `npx supabase link --project-ref <ref>`:

    DIR=backup/$(date +%F)
    mkdir -p $DIR
    npx supabase migration list --linked > $DIR/migrations.txt
    npx supabase db dump --linked -f $DIR/data.sql --data-only --use-copy -s public,app,auth
    npx supabase storage cp -r ss:///task-photos $DIR --linked --experimental

Фото окажутся в `$DIR/task-photos`, пути внутри те же, что в бакете. Для локального стека те же команды выполняются с `--local` вместо `--linked`. Папка `backup` в репозиторий не попадает.

Копии храните вне сервера приложения и с тем же уровнем доступа, что и рабочая база: там персональные данные сотрудников, хеши паролей и рабочие фотографии.

## Восстановление в отдельной среде

Восстанавливать стоит в отдельный проект Supabase, а не поверх рабочего.

1. Создайте пустой проект и примените к нему миграции из репозитория. Версия кода должна совпадать со списком в `migrations.txt`:

        npx supabase link --project-ref <новый ref>
        npx supabase db push

2. Загрузите данные через `psql` со строкой подключения нового проекта (раздел Database settings). Режим `replica` отключает триггеры и проверку внешних ключей на время загрузки, поэтому порядок таблиц не важен:

        psql "$NEW_DB_URL" --single-transaction -v ON_ERROR_STOP=1 -c 'set session_replication_role = replica' -f backup/<дата>/data.sql

3. Загрузите файлы обратно в бакет по тем же путям:

        npx supabase storage cp -r backup/<дата>/task-photos ss:/// --linked --experimental

   Источник указывается папкой `task-photos`, а назначение корнем `ss:///`. Если указать `ss:///task-photos`, всё окажется во вложенной папке и база перестанет находить фото.

4. Проверьте согласованность: у каждой загрузки, привязанной к отчёту, должен быть файл в хранилище.

        select count(*) from public.uploads u
        where u.report_id is not null
          and not exists (select 1 from storage.objects o where o.bucket_id = 'task-photos' and o.name = u.storage_path);

   Ожидаемый результат 0.

5. Проверьте доступ: войдите бригадиром и диспетчером, откройте завершённое задание с фотоотчётом и убедитесь, что фото открываются, а бригадиру другой бригады это задание не видно.

После проверки приложение можно переключить на новый проект, поменяв `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`.

Процедура проверена на локальном стеке: копия снята с рабочего экземпляра и восстановлена во второй, чистый. Совпали все пользователи и пароли, задания, отчёты и загрузки, файлы сверены по SHA-256, ограничения RLS для бригадира и диспетчера другого подразделения работают.
