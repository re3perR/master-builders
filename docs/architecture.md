# Устройство системы

Master Builders — Next.js приложение (App Router) поверх Supabase: Postgres с RLS, Auth и приватное хранилище фотографий. Всё, что меняет данные, проходит через функции в базе, поэтому правила одинаково работают и из интерфейса, и при прямых запросах к API.

## Данные

Организационная структура: компания → подразделения → бригады. Пользователь привязан к одному подразделению через `profiles`, у бригады ровно один бригадир (`crews.foreman_id` уникален), состав бригады — просто список имён в `crew_members`.

Основные таблицы:

- `companies` — название, часовой пояс (по умолчанию Europe/Moscow) и счётчик коротких номеров заданий;
- `divisions`, `profiles`, `crews`, `crew_members`;
- `sites` — объекты подразделения: адрес, примечание о доступе, рабочий контакт, признак архива;
- `tasks` — задания. Номер уникален внутри компании (MB-12), объект и бригада обязательно из того же подразделения (составные внешние ключи `(site_id, division_id)` и `(crew_id, division_id)`), исходные и текущие плановые сроки, снимок адреса и инструкции доступа, отметки сервера о принятии, начале, отправке, завершении и отмене, ссылка на исходное задание, `version` для защиты от устаревших изменений;
- `task_obstacles` — препятствия; частичный уникальный индекс не даёт открыть второе, пока первое не закрыто;
- `task_messages` — обсуждение внутри задания, неизменяемое;
- `task_reports` — версии отчётов 1…n с решением (ожидает, принят, возвращён, отменён вместе с заданием), уникальность `(task_id, version)` и не больше одной ожидающей версии;
- `uploads` — загруженные фотографии: сначала временные, после отправки отчёта привязаны к его версии;
- `task_events` — история задания, которую пишет только сервер.

Время хранится в UTC. Ввод и отображение идут в поясе компании, день для фильтров и расписания тоже считается по нему, поэтому сотрудник с телефоном в другом поясе видит те же договорённости.

## Права

| Действие                                             | Диспетчер                   | Бригадир                 | Руководитель         |
| ---------------------------------------------------- | --------------------------- | ------------------------ | -------------------- |
| Видит задания                                        | своего подразделения        | только своей бригады     | своего подразделения |
| Создаёт и меняет условия, сроки, бригаду, отменяет   | да                          | нет                      | нет                  |
| Принимает задание, начинает работу, отправляет отчёт | нет                         | да                       | нет                  |
| Принимает или возвращает отчёт                       | да                          | нет                      | нет                  |
| Открывает препятствие                                | нет                         | да                       | нет                  |
| Закрывает препятствие                                | да                          | да                       | нет                  |
| Пишет в обсуждение                                   | да                          | да                       | только читает        |
| Объекты                                              | создаёт, меняет, архивирует | видит через свои задания | просмотр             |
| Бригады                                              | название и состав           | своя бригада             | просмотр             |

Роль, подразделение и бригада берутся только из серверной сессии и таблицы `profiles`. Аккаунты, роли и подразделения создаются через seed или администратором базы, в интерфейсе нет регистрации и повышения прав.

## Как это защищено в базе

- RLS включён на всех пользовательских таблицах. Политики чтения проверяют подразделение, а для бригадира ещё и бригаду, в том числе для связанных таблиц: сообщений, отчётов, фото, истории, препятствий. Подмена идентификатора в запросе ничего не даёт.
- У роли `authenticated` отозваны `insert`, `update` и `delete` на всех таблицах. Изменения возможны только через функции `public.*` с `security definer` и пустым `search_path`. Каждая функция проверяет сессию, роль, статус и версию задания.
- Переходы статусов, отчёт, решение и запись истории выполняются в одной транзакции. Задание блокируется `select … for update`, поэтому одновременные «принять» и «вернуть» по одной версии отчёта не пройдут оба: второй получит конфликт версии.
- Ошибки имеют свои коды: MB401 нет сессии, MB403 нет прав, MB404 запись не найдена или недоступна, MB409 устаревшая версия, MB422 неверные поля, MB423 действие недоступно в текущем состоянии. Интерфейс показывает по ним разные сообщения и сохраняет введённые данные.

## Повторные запросы

Клиент генерирует ключ для каждой попытки действия и повторяет его при повторной отправке. Функции сохраняют результат в `app.idempotency_keys` и на повтор с тем же ключом возвращают тот же ответ, не создавая второй отчёт, решение или событие. Для сообщений и отчётов дополнительно стоят уникальные ограничения по автору и ключу. Устаревшая версия задания отклоняется с MB409, а интерфейс показывает актуальную карточку.

## Пересечения в расписании

Интервалы считаются полуоткрытыми `[начало, окончание)`: работа до 12:00 и работа с 12:00 не конфликтуют. Учитываются все незавершённые и неотменённые задания бригады, включая проверку и интервалы через полночь. При создании, переносе и переназначении сервер возвращает список пересечений, пользователь подтверждает их, и запрос повторяется со списком подтверждённых. Если за это время появилось новое пересечение, сервер снова вернёт предупреждение.

## Фотографии

Хранилище `task-photos` приватное, публичных ссылок нет.

1. Браузер отправляет фото на сервер приложения. Сервер проверяет размер (до 10 МБ) и реальное содержимое через декодер, принимает только JPEG, PNG и WebP, поворачивает по EXIF и пересохраняет без метаданных, включая геоданные.
2. Функция `register_upload` вызывается с сессией пользователя: проверяет роль, доступ к заданию и статус, создаёт временную запись с размером и типом обработанного файла и выдаёт путь `компания/задание/идентификатор.расширение`. Путь задаёт сервер, клиент выбрать его не может.
3. Обработанный файл кладёт в Storage только сервер приложения, по выданному пути и без перезаписи. Для этой записи он использует service role ключ: это единственное место в приложении, где ключ применяется (`src/lib/supabase/admin.ts`), и только после всех проверок. Ключ есть только в окружении сервера и в браузер не попадает. У пользователей нет политики на запись в `task-photos`, поэтому прямой запрос к Storage с их сессией отклоняется даже по выданному пути. Удалить можно только свой неотправленный файл.
4. `submit_report` блокирует выбранные временные записи, проверяет, что все фото есть в Storage, совпадают с записью по размеру и типу, принадлежат автору и этому заданию и ещё не использованы, затем в одной транзакции создаёт версию отчёта, привязывает фото, меняет статус и пишет историю. Если в это время фото удаляют в другой вкладке или очисткой, удаление либо ждёт отправки и ничего не трогает, либо отправка получает ошибку: отчёт не публикуется с меньшим числом фото, чем выбрал бригадир.

Просмотр фото идёт по подписанным ссылкам, которые сервер создаёт после проверки доступа и которые живут несколько минут. После выхода новые ссылки не выдаются.

Storage и база не имеют общей транзакции, поэтому после неудачной отправки могут остаться временные файлы. `npm run cleanup:uploads` удаляет временные загрузки старше 24 часов и файлы без записи в базе. Фото, привязанные к отчётам, скрипт не трогает. В пилоте его стоит запускать по расписанию раз в сутки.
